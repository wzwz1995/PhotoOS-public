# 70 · 安全边界与硬规则

> 本篇把项目里那些"看起来多余"的防御逐条落到代码。它的读者是**要改代码的人**：
> 这里每一条都对应一个真实发生过的故障或一条产品级承诺，动它们之前请先看"违反后会怎样"。

## 0. 威胁模型：防的是自己点错，不是防黑客

【实测】服务**有意不做鉴权**，默认只监听回环地址，理由写在代码里：
"纯本地服务……没有鉴权也有意如此（单用户本地优先）"（`photoos/backend/photoos/api/app.py:4`），
且"破坏性操作在此层**没有入口**"（`app.py:8`）。

【推断】由此推出本篇其余各节的共同形态：**边界都设在"防止误操作与代码缺陷"上**，
而不是"防外部攻击者"。所以你会看到"二次确认""白名单""词法校验"这类机制 ——
它们防的是：用户手滑、路径拼接写错、UI 传上来的参数没校验。

## 1. 铁律 #1：原片只读

**规则**：唯一会往照片库写文件的模块是 `library/importer.py`，且**只复制** ——
不改名、不移动、不删除源文件；其余模块碰原片只允许 `open(..., 'rb')`。

**代码落点**：

| 机制 | 位置 | 说明 |
| --- | --- | --- |
| 导入是唯一写入能力 | `photoos` CLI 帮助文本：`import` 标注"唯一写入照片库的能力，默认只预演" | 【实测】`python -m photoos --help` |
| 默认只预演 | `import` 需显式 `--apply` 才落盘 | 【实测】`import --help` 有 `--apply` 开关 |
| 派生数据落在本地 | 预览/缩略图写 `data/`，不写原片盘 | `api/app.py:3650-3651` |
| 路由级守卫 | 禁止出现"动原片"的端点（路径动作词判据） | `tests/unit/test_api.py:600-609`（见 §5.2） |
| 仓储层守卫 | 精选/主题的增删**不做任何文件系统调用** | `repos/__init__.py:663-664,882` |

**铁律原文**（【实测】`photoos/README.md:17`）：
> **原片永不被动**：PhotoOS 不移动、不改名、不覆盖、不删除照片原文件。**删除数据库记录 ≠ 删除原文件。**

**违反后会怎样**：用户不可恢复的数据损失。这是**产品底线**，不是实现细节
（`docs/01-arch.md:99-100`）。
**取证状态**：本会话**没有**逐行审计 `importer.py` 的全部写入调用
（那属于 [`30-媒体与导入流水线.md`](30-媒体与导入流水线.md) 的取证任务），
因此上表只证明"能力边界存在"，**不声称"已证明不存在其他写入路径"** —— 见
[`90-未解问题与待确认.md`](90-未解问题与待确认.md)。

## 2. 铁律 #2：数据库里的路径永远是相对的

**规则**（PRD §5.2 LOCKED）：库里**只**存相对 Library 根的路径，用反斜杠分隔；
相对路径**必须**拒绝盘符、UNC、`\\?\` 设备命名空间、前导分隔符、连续分隔符、
空路径段与 `..`。任何 `Path.relative_to` 的结果都必须过 `validate_relative()` 才能入库。

【实测】这套校验完整实现在 `library/paths.py`，单一入口，**非法即抛错、绝不静默修正**：

| 拒绝的形态 | 代码 | 抛出的 kind |
| --- | --- | --- |
| 设备命名空间 `\\?\` | `paths.py:51-54` | `device_path` |
| UNC `\\server\share` | `paths.py:55-58` | `unc_path` |
| 盘符 `C:` / `E:` | `paths.py:59-63` | `drive_letter` |
| 前导分隔符（绝对路径） | `paths.py:64-68` | `leading_separator` |
| 连续分隔符 / 空段 | `paths.py:69-73`、`79-82` | `empty_segment` |
| `..` 上跳 | `paths.py:74-78` | `parent_traversal` |

> 【实测】`paths.py:1-8` 的模块文档把"为什么"写清楚了：
> **"保证「盘符永远不会成为照片的永久身份」这一条在代码层面无法被绕过"**。
> 【推断】这条规则的现实价值：照片盘换盘符（`E:` → `F:`）或换机器时，
> 库里的身份不变，只需重新绑定卷，而不是全库重建。

### 2.1 预览服务：词法校验 + **不许顺着联接解析**

【实测】`/api/assets/{id}/thumb|preview` 的路径解析在 `api/app.py:3650-3686`。
关键设计（`app.py:3663-3676` 的注释）：

1. 从 `preview` 表取出**相对** `data_root` 的 `path`；
2. 用 `paths.join_relative()` 做**纯词法**校验（拒绝 `..`/盘符/UNC/绝对路径）；
3. **校验通过之后**才真正去读文件（此时才允许顺着目录联接）。

**为什么不能"先 resolve 再判断在 root 之内"**：`data_root` 内部完全可能是目录联接
（例如把缓存挪到另一个盘再联回来）。一旦顺着联接 resolve，目标就落到 `data_root` 之外，
"candidate 必须在 root 之内"**永远不成立** → 文件明明存在却全部 404。
代码注释记录了真实现场：**"用 `mklink /J` 联接真实 `thumbnails/` 做演练时，
`/api/assets/{id}/thumb` 全部 404，界面缩略图全是坏图"**（`app.py:3675-3676`）。

> ⭐ 这是本项目最值得学的一条工程经验：**"包含在 root 内"与"解析联接"本身互斥**。
> 想同时要安全和可用，就必须把"词法校验"和"文件系统解析"分成两步，而不是合成一句
> `resolved.is_relative_to(root)`。

### 2.2 导出目录：判据是"解析后的父目录相等"

【实测】`POST /api/exports/reveal` 的入参来自客户端，代码注释写明了它的危险性：
"不设限就等于给了'让服务端对任意路径起一个进程'的能力"（`api/app.py:3097-3099`）。
判据是 `resolved.parent != allowed` → 403（`app.py:3106-3112`），
**而不是字符串前缀匹配** —— 因为后者能被 `..\` 绕过（注释原话）。

## 3. 命令执行：浏览器只能提交 action id

**规则**：浏览器**永远不能提交命令字符串**，只能提交一个预先定义的 `action id`；
命令模板、参数拼接、用哪个解释器，全部由服务端决定。

【实测】这条边界的实现与理由集中在 `actions/catalog.py:9-24`：

| 机制 | 位置 | 说明 |
| --- | --- | --- |
| 只有 id 来自浏览器 | `catalog.py:11-14` | "即便有人能访问 `127.0.0.1:8760`，他能做的也只有触发预先定义好的命令" |
| 模板展开 | `catalog.py:resolve_argv()` | "用户输入**只可能**出现在 query 那一个位置" |
| 搜索词字符白名单 | `catalog.py:39` | `^[\w\u4e00-\u9fff][\w\u4e00-\u9fff \-·.,、，。/]{0,39}$`，"故意收得很紧" |

## 4. 前端资源的缓存边界（一条由故障换来的规则）

【实测】`/` 与 `/static/*` 一律 `Cache-Control: no-cache` + ETag（`api/app.py:3364-3379`）。

**为什么**（`app.py:3348-3363` 注释）：原先两者都没有 `Cache-Control`，
浏览器走**启发式缓存**，改完前端后用户看到"旧 JS + 新 HTML"，
症状是"新做的控件出不来"，`Ctrl+F5` 才好。本项目**零构建、文件名无内容哈希**，
所以正确策略是"允许缓存，但每次必须回服务端校验"。

⚠️ **改动风险**：这条规则**看起来像"多余的一行头"**，删掉后一切"正常"，
故障只在"改了前端之后"出现，且**每个人都会先怀疑自己没刷新**。
配套事实：前端改动**不需要重启服务**，后端改动**必须重启**，
而且 `/api/health` 会撒谎（`NEXT_SESSION_PROMPT.md:47`）。

## 5. 破坏性操作与"不能有的功能"

### 5.1 铁律 #5 的实际执行方式：**写死在端点里**

【实测】真正拦住破坏性操作的不是配置项，而是端点自己：

| 端点 | 行为 | 出处 |
| --- | --- | --- |
| `DELETE /api/collections/{id}` | 不带 `?confirm=true` → **428**「删除主题需要二次确认」 | `api/app.py:1691-1703` |
| `DELETE /api/people/{id}` | 同上 | `api/app.py:2443-2458` |

【实测】两处注释都写着"**铁律 #5**：破坏性操作必须二次确认"。
【推断】用 428（Precondition Required）而不是 400，是很贴切的选择：
它表达的是"**请求本身没问题，但你还没满足前置条件**"。

### 5.2 路由级守卫：不许出现"动原片"的入口

【实测】`tests/unit/test_api.py:600-609` 的 `test_no_destructive_endpoints`
遍历**所有路由**，要求路径里不出现破坏性动作词（判据在 `tests/unit/route_guard.py`）。
另有一条**反证测试**（`:612-622`）双向钉住判据本身：真正的破坏性路径必须认得出来
（`/api/assets/{id}/delete` 等），而 `confirm-all`（含 `rm` 两个字母）不能被误伤。

⚠️ **这个守卫必须读准**：它禁止的是**路径里的动作词**，不是所有删除操作。
`DELETE /api/collections/{id}` 的路径词是 `collections`，**合法通过** ——
它删的是用户的**主题**，不是照片。产品级表述见 PRD §11.1 / §14.7。
【实测】本项目有一次真实摩擦：某轮把端点命名为 `/items/remove`，
被这条守卫拦下，作者**改名字（`detach`）而不是放宽守卫**
（`PHASE2_TECH_PLAN.md:1299`）—— 放宽它等于把守卫变成摆设。

### 5.3 其余"不能有/不能显示"的东西

| 规则 | 现状 | 出处 |
| --- | --- | --- |
| 服务端**没有删除原片的入口** | Phase 1 不提供删除能力 | 【实测】`api/app.py:8` + 上面的路由守卫 |
| 资源管理器"定位文件"是允许的 | 只起文件管理器，不改文件 | 【实测】`api/app.py` 路由表 |
| **界面不许出现评分/推荐语言** | PRD §9.2 LOCKED；金色 = "你的选择" | `docs/01-arch.md:101-102`、`docs/README.md:51-52` |
| 界面不许出现 PRD 章节号/铁律/决策编号/"实测"等内部语言 | 有文档级检查脚本 | 【实测】`HANDOVER.md:653`、`PHASE4_DELIVERY.md:569` |

> ⚠️ 【实测】**一处需要留意的事实**：`require_confirmation_for_destructive`
> 在整个后端**只出现两次** —— 定义（`config.py:204`，默认 `True`）与下发给前端
> （`api/app.py:3342`）。**没有任何服务端代码读它来做判断**（全仓 grep 仅这两处）。
> 【推断】这是因为铁律 #5 是**逐端点写死**的（见 §5.1），配置项只是下发给客户端的标志。
> 【推断】这与"服务端没有破坏性操作入口"是自洽的：既然没有可破坏的操作，
> 服务端确实不需要拦。但这意味着该开关目前**只是一个下发给客户端的标志**，
> 真正的拦截（若将来加了破坏性操作）**必须在新增入口时一并实现**，
> 不能假设"配置已经是 True 所以已经安全"。→ 已登记为 Q-4。

> 【推断】"删除能力不存在"比"删除前弹窗确认"更强：**没有入口 = 没有绕过路径**。
> 若要新增删除能力，必须同时改 PRD §9.2 与本篇 —— 这属于产品决策，不是实现细节。

## 6. 数据安全：备份与恢复的正规入口

【实测】正规备份是 `photoos backup`（在线 `VACUUM INTO`，支持 `--label`/`--keep`/`--list`）
与 `photoos migrate`（换机迁移包：导出/校验/导入）。

⚠️ 【实测】**`data/` 目录里同时躺着两个非托管遗留文件**：
`photoos.db.bak-before-scene-prune`（214.04 MB）与 `config.json.bak-before-ai-python`。
它们是历史操作的现场遗留，**不在任何恢复流程里**。
【推断】让它们留在 `data/` 的风险是：将来"恢复"时**很可能被误当成备份用**。
建议（需你确认，见 [`90-未解问题与待确认.md`](90-未解问题与待确认.md)）：
要么移入 `data/backups/`，要么在文件名上明确标注"不要用于恢复"。

## 7. 一条"静默失效"类缺陷的通用教训

【实测】项目记录了两类**不报错**的失效，值得独立记住：

| 现象 | 为什么不报错 | 记录位置 |
| --- | --- | --- |
| RAW 预览二次旋转（3,861 张）→ 人脸特征失效 | 检测器照样给 0.87 置信度、框也框得准，只是特征崩了；日志干净、断言全绿 | `HANDOVER.md:1168-1169` |
| 前端"旧 JS + 新 HTML" | 浏览器启发式缓存不报任何错 | `api/app.py:3350-3353` |

> 【推断】共同点：**"缺少校验线索"时，系统会安静地用旧的东西**。
> 所以本项目在关键路径上倾向于"每次回服务端校验""把图下下来看"这类
> **主动制造线索**的做法，而不是"相信缓存/相信断言全绿"。
