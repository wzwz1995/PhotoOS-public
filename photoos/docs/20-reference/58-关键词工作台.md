# 58 · 关键词工作台（画面词刷新与向量补算）

> **状态**：P0/P1/P2 + 场景复核 MVP 已实现（2026-10-22），全量验证见 §6.4。
> 本文先落方案，再按这里的 P0/P1/P2 实施。
> **相关代码**：`photoos/backend/photoos/api/app.py`、`photoos/backend/photoos/library/semantic_rank.py`、
> `photoos/backend/photoos/library/embed_pipeline.py`、`photoos/backend/photoos/web/js/search.js`。
> **相关表**：`semantic_query`、`semantic_query_hit`、`semantic_feedback`、`semantic_tuning`、`embedding`。

## 1. 问题

「找照片」读的是两张**快照表**：

- `semantic_query`：词的文本向量（EmbeddingGemma 2，768 维）；
- `semantic_query_hit`：这个词上一次计算时命中的拍摄组。

它们都不会随着新照片入库自动更新。

2026-10-21 的真实库：

| 项目 | 数值 |
|---|---:|
| Asset | 28,151 |
| 有 EG2 向量 | 21,400 |
| 没有 EG2 向量 | 6,751 |
| 其中有 preview、可补算 | 6,737 |
| 缺 preview、暂时算不了 | 14 |
| 画面词 | 45 |
| 命中快照 | 2,740 条，最后计算于 10-18 |

因此新照片**不会**被已有画面词搜到，界面也没有任何提示。这是“结果安静地过期”，比功能缺失更难被发现。

补算完成后的同一天实测：

| 项目 | 数值 |
|---|---:|
| 有 EG2 向量 | 28,137 / 28,151 |
| 缺 preview、暂时无向量 | **14 个视频**（视频库 #2，不是照片） |
| 45 个词刷新后命中 | 9,000 条 |
| 过期词 | 0 |
| GPU 补算耗时 | 1,184.8 秒（约 19.7 分钟，6,737 张） |

## 2. 关键判断

### 2.1 词的文本向量不需要因为新照片而重算

一个词的文本向量只取决于模型和 `prompt_text`。新照片进来，变的是**图片向量**和**命中快照**，不是词向量。

### 2.2 重算命中不需要 AI 运行时

命中 = 已有图片向量 × 已有词向量，再做余弦排序。`serve` 进程可以用 numpy 完成，不需要 torch。
所以“更新选中关键词”可以做成**秒级**操作。

### 2.3 补图片向量是全局动作，不是按词分摊

6,737 张图片的向量是所有词共用的。选中 10 个词不会让补算更快；它只是决定补完后刷新哪几个词。

### 2.4 补图片向量的成本必须如实展示

当前 AI venv 是 CPU 版 torch：

- 干跑实测：**4,918 ms/张**；
- 6,737 张约 **9.2 小时**；
- 机器有 RTX 3060，但 `torch.cuda.is_available()` 为 False；
- 换 CUDA 版 torch 后，代码里记录的 GPU 约 **320 ms/张**（6,737 张约 36 分钟），开 AMP 还可能更快。

不能把 9 小时任务藏在“更新关键词”按钮后面。必须独立入口、明确 ETA、可暂停、可续跑。

## 3. 产品方案

入口在「找照片」页：

- 顶部状态条**只在有照片缺向量时**出现；视频库缺 preview 不写成“照片缺预览”。
- 按钮「管理关键词」打开工作台；视频/照片缺口、preview 说明都在工作台覆盖区。

工作台是表格 + 批量操作，不新建一个顶级视图。
**添加关键词也在工作台内**：填「关键词 + 实际 prompt → 添加并计算」，
复用 `search_rebuild`，不再要求用户先回搜索框触发一次空态。

每个词的结果池最多存 `TOP_HITS = 200` 组候选；界面显示 `200+ 组` 表示
**到了快照上限**，不是“全库只有 200 组匹配”。原始 CLI 的 `--top` 同样是
候选池，不是精确命中数。

```
[全选] [只选待更新]
□ 月亮     prompt: 月亮          候选 35 组   上次 10-18
□ 黄昏     prompt: sunset...     候选 39 组   上次 10-18
...

[重算选中候选（秒级）] [补算新照片向量…（后台）] [改词义]
```

每行显示：

- 关键词、实际 prompt；
- 候选池组数（到 200 上限时显示 `200+`）；
- 上次重算时间；
- `keep / drop` 反馈数；
- 状态：结果完整 / 有新照片未参与 / 缺 preview。

### 3.1 重算选中候选

- 选中的词，按当前图片向量与已存词向量重新算命中；
- 不碰反馈与 tuning；
- 事务内替换 `semantic_query_hit`；
- 秒级完成，不创建后台任务。

### 3.2 补算新照片向量

- 全局动作，不按选中词分摊；
- 通过 AI venv 跑 `embed --engine gemma --apply`；
- 后台任务，显示已算/待算/预计剩余；
- 完成后再对选中词执行 3.1；
- 缺 preview 的单独列出，不阻塞其他资产。

### 3.3 改词义

- 编辑 `prompt_text`（“实际送进模型的提示词”）；
- 动作 `search_rebuild` 调 CLI `search <词> --prompt <新 prompt> --save --top 200`；
- 文本向量与命中一起替换；
- 这是“更准”的真正入口；只刷新命中不会自动让词义变准。

### 3.4 场景复核（MVP）

关键词工作台每行新增「发现」，打开场景复核页：

- 识别线滑杆（0.40–0.99）控制候选范围；
- 点卡片图片打开原片大图弹窗；
- 统计只显示“识别线以上未确认 / 未确认总量 / 本轮只取 N 张”，不把过线池
  误读成本轮会全部展示；
- 用已确认正负例估算建议识别线，并显示估算精确率/覆盖；如果建议线以上
  没有未确认候选，明确提示“高分区间已经基本筛完”，不再给一个会诱导继续
  拉低线的按钮；
- 前 3 轮（含冷启动）：**40 不确定 + 20 确定**；
- 第 4 轮起：**40 确定**；确定不足时用不确定补；
- 每张「是 / 不是」立即写入 `semantic_feedback`（keep/drop），下一轮训练直接使用；
- 「本批剩余全部是 / 全部不是」只处理未标记卡片，不覆盖已确认标签；
- 场景标签是唯一稳定数据；没有“确认找全”终态；
- 新照片本来就在全库池里，下一轮发现自动参与。

当前的场景分是**正例均值 − 负例减分**的轻量 prototype，不依赖 torch；
它不是逻辑回归，但已经能把“人工确认”变成全库打分与识别线筛选。后续可在
同一标签集上升级成线性分类器，不需要重做 UI。

状态存在 `semantic_scene`（`threshold` / `round`），标签仍复用
`semantic_feedback`；接口：

- `GET /api/semantic/scenes/{query_id}`
- `POST /api/semantic/scenes/{query_id}/discover`
- 标签：`POST /api/semantic/feedback`（不新增一套标签 API）

### 3.5 实测后的补充

- CUDA 版 torch 已在本机验证：`torch 2.14.1+cu130`，RTX 3060 6GB，234.2 ms/张；
- 6,737 张 GPU 预计约 26 分钟（CPU 同口径约 9.2 小时）；
- 补向量任务用现有 `embed_gemma` 动作，所以进度、暂停、取消都复用任务系统；
- 任务运行期间不要重开 PhotoOS，否则子进程会被终止；向量是增量写入的，重跑会接着算。

## 4. 接口

### GET `/api/semantic/manage`

返回：

```json
{
  "coverage": {
    "model": "embeddinggemma-2",
    "model_version": "safetensors-fp32",
    "prep_version": "eg2-p1.0",
    "total_assets": 28151,
    "embedded": 21400,
    "missing": 6751,
    "missing_with_preview": 6737,
    "missing_without_preview": 14,
    "last_hit_at": "2026-10-18T04:58:02+08:00"
  },
  "items": [
    {
      "id": 1,
      "query_text": "月亮",
      "prompt_text": "月亮",
      "hit_count": 35,
      "last_hit_at": "2026-10-18T04:58:02+08:00",
      "feedback_keep": 2,
      "feedback_drop": 1,
      "stale": true
    }
  ]
}
```

### POST `/api/semantic/refresh`

请求：

```json
{ "query_ids": [1, 2, 3] }
```

行为：

- 只重算候选池，不重算词向量；
- 不要求 AI 运行时；
- 返回每个词写入的候选数（最多 200）。

### POST `/api/actions/embed_gemma/run`

复用现有动作，不新增重复命令。前端拿到任务后轮询进度，完成后调用 refresh。

### POST `/api/actions/search_rebuild/run`

P2：

```json
{ "query": "黄昏", "prompt": "sunset over the horizon" }
```

行为：

- 通过动作层校验 query / prompt；
- 在 AI venv 跑一次 `search <query> --prompt <prompt> --save --top 200`；
- 文本向量与命中快照一起替换；
- 没有 AI 运行时时动作 `available=false`，并说明缺什么，不静默改库。
- 不新增独立的 `/api/semantic/.../prompt` 路由：改词义本来就是一条
  受白名单保护的外部命令，复用现有动作系统比再写一套子进程更安全。

## 5. 数据与一致性

- 命中刷新只写 `semantic_query_hit` 和 `semantic_query.updated_at`；
- 反馈表 `semantic_feedback`、重排表 `semantic_tuning` 不动；
- `save_hits()` 已经保证只写活跃 Shot、删除旧命中、幂等；
- 刷新前校验：
  - 词的模型身份与图片向量身份一致；
  - 向量字节长度 = `dim × 4`；
  - 没有向量的资产不计入；
- 刷新后 `semantic_pool` 的进程内缓存不失效（图片向量没变）；
- 补向量后向量条数变化，现有 `_semantic_pool` 按 count 失效并重建。

## 6. 性能与验收

### 6.1 命中刷新

- 目标：45 个词全部刷新 < 5 秒；
- 实测方法：`semantic_rank.build_pool()` + `pool.matrix @ query_vector`；
- 不允许逐词重新读取 65 MB 向量池。

### 6.2 补向量

- CPU：约 9.2 小时（4,918 ms/张）；
- CUDA：按代码里的 320 ms/张，约 36 分钟；
- 必须先跑 `--limit 50` 做真实速度抽检，再决定全量；
- 支持暂停/续跑，已写入的向量不丢。

### 6.3 验收

1. 工作台能列出 45 个词；
2. 选中 2 个词，点更新，命中数变化可见；
3. 新照片补向量后，旧词能搜到它们；
4. 反馈与 tuning 不被刷新抹掉；
5. 缺 preview 的 14 张有明确说明；
6. 无 AI 运行时时，刷新命中仍可用；补向量和改词义给出可操作提示；
7. 真实 Edge 探针覆盖打开工作台、勾选、更新、提示；
8. `pytest` 全量通过。

### 6.4 已完成验证（2026-10-21）

- `pytest tests`：**1403 passed / 19 skipped / 0 failed**（380.25 秒）；
- 真实 Edge `semantic_manage.py`：覆盖提示、45 词、2 词刷新、关闭 PASS；
- 真实补算：6,737 张，CUDA，**1,184.8 秒**；补后 28,137/28,151 有向量；
  剩余 14 个全部是视频库资产（`PENDING`、无 preview），主搜索栏不再用
  “14 张照片缺预览”这种会误导照片搜索的文案；覆盖详情只在工作台内展示。
- 45 个词刷新共 **9,000 条** 命中；`query_text=月亮` 的 200 条命中中，
  有 113 个 Asset / 81 个 Shot 来自新导入批次；
- 反馈 / tuning 在刷新中保持不变（单测与真实库均验证）。

## 7. CUDA 可选组件

CUDA 版 torch 验证可用后，新增独立可选组件：

- id：`torch-cuda`（或 `gemma-gpu`）；
- 前置：`gemma-text` 已安装；
- 安装：在 AI venv 中安装与 CUDA 匹配的 torch/torchvision；
- 检测：`torch.cuda.is_available()` 为 True 才算安装成功；
- 卸载：回退 CPU 版 torch，不能把 AI venv 弄坏；
- 界面明确写“给 EmbeddingGemma 加速，不是 ONNX Runtime GPU”。

ONNX Runtime GPU 只服务 CLIP/人脸等 ONNX 模型，不能替代 CUDA torch。

## 8. 分期

- **P0**：速更新命中 + 覆盖状态 + 工作台表格；
- **P1**：补向量后台任务 + 完成后自动刷新；
- **P2**：改 prompt / 重建词义；
- **P3**：CUDA torch 可选组件（本机 CUDA 验证通过后）。

P0 不依赖 GPU，也不依赖补完 6,737 张；它先解决“结果静默过期”。
