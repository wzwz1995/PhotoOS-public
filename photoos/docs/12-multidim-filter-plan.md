### 补 1 · 元数据关键词搜索 ✅ 已完成

顶栏筛选台现在是**五组**：内容 / 元数据 / **关键词** / 人物 / 输出。

关键词给它**自己的分组**，因为它和相邻两组都不是一类：

| 维度 | 怎么找 | 找什么 |
|---|---|---|
| **内容** | 模型算画面相似度 | 看起来像"日落"的 |
| **元数据** | 结构化下拉（年份/机型/镜头/焦距/类型/状态） | 字段等于某个值 |
| **关键词** | SQL 的 `LIKE` | 文件名 / 机型 / 镜头里含这串字的 |

三者混在一个框里，用户不会知道自己在搜什么。

> ⚠️ 顺手清掉一个旧病：`#filter-q` 原来被绑了**两次** `oninput`
> （350ms 与 260ms 各一次，后者覆盖前者）—— "同一件事写两遍"正是这一轮要清掉的病。

**验证**：`_probe/library_filter.py` 新增关键词断言；`filter_layout.py` 加上
"五个分组都在"与关键词字段的存在性。

> ⚠️ 关键词那条断言我改过**两次**，两次都是**用例没准备好前置条件**：
> 第一次它在"两个人"的条件下跑（那两人在 `DSC_1894` 上没有照片 → 0 张），
> 我把 0 当成了"功能坏了"；第二次修了基准，但探针的 `total()` 把
> 「没有匹配的照片」读成 `None` 而不是 `0` —— **0 是合法结果**，不是"读不到"。
> 同一个教训在这一轮里出现第四次了，见 `_probe/README.md`。

### 第 4 步 · 弹窗三级渐进 + 可操作标签 ✅ 已完成

**问题**：`await Promise.all([详情, path, collections])` —— 等最慢的那个（详情 110 ms）
才显示任何东西。加标签只会更慢。

**三级渐进**：

| 级 | 内容 | 实测 |
|---|---|---|
| ① | 立刻显示：用网格里**已解码**的缩略图占位 | **34 ms** |
| ② | 路径 + 标签（人名 / 内容命中 / 精选状态） | 同批 |
| ③ | 元数据表 + 大图替换占位 | **76 ms** |

**标签合成一行**（不是三个区块）：精选状态下拉 + 内容命中 + 人物。
交互统一为两个：**点标签 = 按它筛**（关弹窗回网格，**替换**现有条件而不是叠加）；
**× = 解除/否决**（内容走同一套表态接口，会真的重排；人物给出口去人物页，
因为归属是**脸级**的）。

**为什么常态不臃肿**：实测 94% 的照片没有任何已归属人物、内容命中也不是每张都有 ——
所以这一行多数时候**整块不出现**。

**验证**：`_probe/modal_tags.py` —— 打开耗时、占位图→大图、标签行、
状态写入后端、点标签筛上，全部通过。

> ⚠️ 占位图那条我踩过一次：第一版用 `grid.lastPainted()` 记"最后画过的卡"，
> 但它只是池子里最后一格（**实测点第 1 张时它是第 35 张**），永远不匹配。
> 改成**从 DOM 按 `data-asset` 找**（虚拟网格只渲染可见格，用户点的那张一定在里面），
> 且要求 `complete && naturalWidth > 0`（没加载成功的不算占位图）。

### 补 2 · 对齐 ✅ 已完成

用户的话是"文案在这里，两边对不齐我好难受"。查下去发现**是同一个病在三处发作**。

**根因**：`.wb-field-inline` 原本是 `display:flex`，**标签宽度 = 文字自然宽度**。
「相邻时间阈值」五个字与「时段」两个字，控件当然错开。

**改法不是逐处硬写宽度，是给一个令牌**：

```css
/* tokens.css —— 只定义一次 */
--wb-label-w: 96px;
```

`.wb-field-inline` 变成 `grid-template-columns: var(--wb-label-w) 1fr`。
**一个令牌值，三处同时对齐** —— 对齐是结构性的，不是调出来的。
另外 `.field` 的 `margin-bottom` 统一归零，行距不再参差。

输出组的 `#load-more` 从"浮在底部的裸按钮"收进网格成为一格
（实测 `w=241`，撑满该组，与「排序」「每页」共用同一条左边缘）。

**验证**：`_probe/filter_layout.py`

| 断言 | 实测 |
|---|---|
| 五组标题在同一基线 | `headTops=[104,104,104,104,104]` |
| 「标题→首标签」间距一致 | `headGaps=[8,8,8]` |
| 同组控件等高 | `heights=[38]` |
| 每列行顶成等差数列 | `{元数据:[159,228,296], 输出:[159,228]}` |
| **精选页标签共用一条竖线** | `labs=[73]` |
| **精选页控件共用一条竖线** | `lefts=[179]` |
| 无过窄控件（<88px） | `[]` |

> ⚠️ **最值钱的教训：`display:none` 的元素量出来全是 0。**
>
> 探针第一版的顺序是"去精选页点一下（触发懒加载）→ 切回照片库量筛选台 →
> 回头再量精选页"。精选页那几条因此拿到一堆 `0`，看着像"错位得离谱"，
> 我差点去改 CSS。
>
> 元素在、CSS 也对，只是**当时不可见** —— 隐藏元素的
> `getBoundingClientRect()` 返回全零矩形。改成**在页面还可见时就地断言**，
> 立刻全绿；独立脚本（不切视图直接量）给出同样的 `73 / 179`。
>
> **任何测量型断言，必须先确认被测对象当时可见。**
> 隐藏元素不是"量出 0"，而是"量的根本不是布局"。已写进 `_probe/README.md`。

> ⚠️ **模板字符串里的反引号会提前闭合字符串。**
> 在 `review.js` 的模板串内部写 HTML 注释，注释里带了反引号（`` `.wb-field` ``），
> 于是后面的 `field` 被当 JS 求值 —— 整个精选页只报一句 `field is not defined`。
> **注释不改变词法。** 新增 `_probe/lint_backticks.py` 守门。

### 补 3 · 控件高度归一 ✅ 已完成

补 2 解决的是"**标签宽度**不一致"，用户接着报维护页也没对齐 ——
那一处更深：**控件高度有两个真源**。

```css
/* 改前 */
select, input[type="text"], … { min-height: 38px; }   /* 38 */
.btn { min-height: 42px; … }                          /* 42（由内容算出） */
```

并排时**输入框比按钮矮 4px**。改成令牌 `--control-h: 42px`，
`.btn` 与全部输入类控件一律 `height: var(--control-h)` + `box-sizing: border-box`
—— **高度由一个数决定，不再由内容决定**。
`textarea` 不共用（多行控件，只共享配色与描边）。

同时修掉两处会重新引入漂移的地方：

- `.row` 原本是 `align-items: stretch`（默认），`.field` 的 `margin-bottom`
  在横排里就是 **8px 死区**。现在 `.row` 按**底边**对齐 + 行内字段去掉纵向边距。
- 维护页「预演抽样」原为 `field inline`（标签在左），同桌其余四格标签在上 ——
  只有它横着摆，控件就比旁边高 8px。去掉 `inline`，结构统一。

**验证**：`_probe/maintenance_layout.py`（新增），1600 / 1100 / 900 三档视口，
**逐行**判定（同一行内控件对齐、标签对齐、输入框与按钮同高 42px）。

> ⚠️ **这一轮抓到的最贵的失真：探针的视口一直不是它以为的那个。**
> `--window-size` 在无头 Edge 下**不生效** —— 实测请求 1600/1100/900
> 三种宽度，`window.innerWidth` **一律是 500×320**。
> 症状很误导：按两个宽度各量一次、**数字一模一样**，看着像"响应式没生效"。
> 而这是**六支探针共用的写法**，也就是说七视图截图与各种几何测量
> 此前全都跑在一个 500×320 的窗口里。
> 修法：`_edge.set_viewport()`（CDP `Emulation.setDeviceMetricsOverride`），
> 十一支探针全部接上，并**回读打印真实视口**。

## 三、硬约束（违反即返工）

1. **原片只读。** 只有 `library/importer.py` 写照片库，其余一律 `open(..., 'rb')`。
2. **不做"评分/推荐"。** 没有星级、没有"最佳"、没有"匹配度 87%"。
   金色 = **你的选择/当前项**，不是"更好"。相似度是**可核对的原始数**，不是评分。
3. **令牌只在 `tokens.css` 定义一处。** 新组件用现有令牌，不自造圆角/字号。

7. **`person_face` 是脸级的，且下游依赖它。** `person_profile`（"再找找像他的"）
   按脸算原型 —— 只写照片级标签不参与学习，界面上**不许假装它有效**。

## 四、执行步骤

### 第 1 步 · 照片库把"文件"呈现成"照片" ✅ 已完成

**先纠正计划初稿里的两个错误事实**（都是勘察后才发现的）：

1. 我写过"连拍帧在照片库里看不到" —— **不成立**。`/api/assets` 本来就是按"张"列的
   （`total = 21400`，同一个 shot 返回多行）。帧一直都在。
2. 我写过"RAW 那格在浏览器里出不了图" —— **也不成立**。实测 50 条 RAW
   **全部** `has_thumb=True`。

所以真实问题只剩**呈现**：同一张照片的 JPG 与 NEF 显示成**两张一模一样的卡**，
网格长度凭空翻倍，画面上又分不清哪张是哪个文件 —— 用户在照片库里看到的是"文件"。

**做法**：给同组文件一个**看得出的家族感**，但**绝不折叠**。

- `fileGroup(index)` 只看**相邻**项（`/api/assets` 按拍摄时间排序，同组文件本来就相邻，
  实测前 12 条是成对出现）。不为了"找全同组"去全表扫描 —— 那会拖垮虚拟网格。
- 成组的卡片加 `.is-stacked`（顶边一条皇家蓝细线）+ 角标写成 `NEF · 2/2`
  （类型 + 组内位置），`title` 说明"这张照片在库里有 N 个文件"。
- **顶边线用中性/皇家蓝而不是金色**：金色在本应用专表"当前项/你的选择"
  （视觉纪律见 `phase2.css` 顶部），拿来表示"同组"会污染那个语义。
- 卡片有 `contain: strict`，所以只能用顶边线这种不越界的手法。

**验证**：`_probe/library_files.py`

| 断言 | 结果 |
|---|---|
| 同组文件带 `is-stacked`、角标形如 `NEF · 1/2` | ✓ |
| **不折叠**：同组文件仍逐个可见 | ✓ |
| **不变量**：`is-stacked` 当且仅当存在相邻同 `shot_id` | 逐张对拍 35 张，0 处不符 ✓ |
| 虚拟网格未退化 | DOM 卡片 30–45，不随总数增长 ✓ |

> ⚠️ 这条不变量断言是**改过一次**的。第一版我写"筛 RAW 之后应当没有成对的"，
> 实测**不成立**：有些拍摄组里就是纯 RAW 多帧（shot 3428 有 **10 个 NEF**）。
> 当时有 15 张带标记，我差点当成"节点复用时旧标记没清掉"去改代码 ——
> 逐张核对 `shot_id` 才确认**标记是对的、断言是错的**。
> 现在改成直接断言"标记与数据的对应关系"，顺带也覆盖了复用路径。

### 第 2 步 · 筛选面板从侧栏移到顶栏

**为什么**：用户明确要求；且侧栏已被"目录树 + 浏览轴 + 索引状态"占满。

┌─ 筛选 ────────────────────────────────────────────────────────────┐
│ 内容   [选一个要找的东西 ▾] [或直接打一个词____] [搜索]              │

**验证**：无筛选时筛选区收起、条件条不显示；设一个条件后两者都出现；

### 第 3 步 · `/api/filter` 改为 asset 级输出

**现状**：`/api/filter`（本轮新增）返回 **shot 级**结果，与第 1 步的"按张列"不匹配。

- 输出改为 **asset 级**：一行一张，带 `shot_id`（保留分组）、`asset_id`、`relative_path`、
  `selection_status`、`person_ids`、`score`。
- **内容分的传递**：`shot` 的相似度**下发给它所有的帧** —— 同一组内各帧分数相同。
  这是诚实的写法（模型就是在组粒度算的），**不要**假装每帧有独立分数。
- 排序：有内容词时按 `score DESC, asset.id`；无内容词时按拍摄时间/文件名（沿用现在的 `order`）。
- 同时让 `/api/assets` 也接受同样的筛选参数，或让照片库统一改用 `/api/filter` ——
  **二选一，不要两条并存**（两条并存必然漂移，这是上一轮的教训）。

**验证**：`tests/unit/test_compose.py` 新增对拍测试（同一组元数据条件，
在 asset 层与 `queries._build_filters()` 结果一致）；内容命中总数 ≥ 早前的 shot 级总数。

### 第 4 步 · 弹窗三级渐进 + 可操作标签

**问题**：现在 `await Promise.all([详情, path, collections])` —— **等最慢的 110 ms 才显示**。
加标签只会更慢。实测：详情 110 ms、`path` 13 ms、`collections` 13 ms。

**改为三级**：

| 级 | 内容 | 耗时 |
|---|---|---|
| ① | 立刻显示：用网格里**已缓存的缩略图**占位 + 文件名（卡片上已有） | 0 ms |
| ② | 路径 + 主题 + **标签**（人名 / 内容命中 / 精选状态） | ~15 ms |
| ③ | 元数据表 + 大图替换缩略图 | ~110 ms |

**标签合成一行**（不是三个区块）：

```text
标签   [最终精选 ▾] [月亮 ×] [妈妈 ×]        [+ 人物]
```

**人物交互分档**（实测数据决定）：

| 情况 | 照片数 | 交互 |
|---|---|---|
| 照片里 0 个已归属人物 | **20,088（94%）** | **人物区块整块不显示** |
| 1 个名字 | 1,175 | 一个芯片 |
| 2 个名字 | 125 | 两个芯片 |
| 3 个以上 | **12** | 很少，照常显示 |

**加人流程**：点 `+ 人物` → 展开。**未归属的脸默认不显示**。
- **1 张脸**（1,732 张照片，71%）：选人即认领那张脸，**一次点击**。
- **多张脸**：出现一行**脸裁切块**（`/faces/{id}/thumb`）让用户点一张 ——
  **不在照片上画框**，就是一个横向小条。
  `loading="lazy"`，且只在展开时才加载（一张 15 张脸的照片不该一次解 15 张图）。

**人名列表一次性拉全库并缓存**（40 个人，55 ms），与 `actions.js` 的目录缓存同一套做法。
抽 `js/people_cache.js`（**不要**从 `app.js` 静态 import `people.js` —— 它有 `initPeople()`）。

**验证**：弹窗 0 ms 有内容；打开时**默认不出现任何未归属的脸**；
单脸照片"选人"一次点击完成；多脸照片能指明是哪一张；
改完精选状态后网格里那张卡片同步更新。

### 第 5 步 · 精选页由粗到细 ✅ 已完成

**现状（就是问题所在）**：

```text
第 1 行： Scene（单个决策单元）← 最细，却排第一，用户面对 300+ 项下拉
          时段
第 2 行： 地点 / 拍摄日期 / 关键词   ← 这三样本来就是用来缩小 Scene 范围的
第 3 行： 相邻时间阈值 / 预设        ← 这是分组参数，不是筛选
第 4 行： 加入主题…
```

**改为**：

```text
① 地点  →  ② 拍摄日期  →  ③ 关键词
────────────────────────────────────
④ 选一个场景 · 进入逐组精选      （范围缩小过之后才出现）
```

**「时段」不再是一层。** 第一版把它放在最前，用户否掉了，两点都对：

- **按时间与地点直接筛就够了。** 场景自己带 `city` 与 `captured_from/captured_to`，
  而 `/api/scenes` 不给 `session_id` 就返回全部 303 个（已实测），筛选在客户端做。
  时段只是"一次拍摄活动"的容器，不必当入口。
- **时段的显示名是目录名**，可读性很差。

现在它降级成最后一行里的**可选**选择器 —— 想整体处理一次拍摄活动时仍然够得着。

**可读性修复**（用户明确提的"可读性还很差"）：

| | 改前 | 改后 |
|---|---|---|
| 场景标签 | `万宁市\2025-11-29_0610-1747\2025-11-29 06:10:01` | `2025-07-13 16:06–16:39` |
| 时段标签 | `希腊市 · 2026-10-08_1702_至_10-09_1847` | `希腊市 · 10-08 17:02`（跨天时给出完整区间） |

改用 `captured_from` / `captured_to` 拼（实测 277/303 有值，**275 个是当天**）。
没有时间的退回 `period` 里的日期；再没有就退回原名末段 —— **不编造**。

**实现要点**（都是踩过的坑）：

- **一次性渲染全部层，靠 `hidden` 切换** —— 不能"按层重建 DOM 来显示下一层"：
  那会让正在打字的输入框丢光标（`renderSceneOptions` 里已为这个坑写过注释）。
- **第④层的判据不是"有可见场景"**。第一版写成 `visibleScenes().length > 0`，
  结果刚进来就显示（"全部 303 个场景都可见"也满足它），**整个漏斗被绕过**。
  现在要求"真的筛掉了东西"（`filtered < total`）。
- **空态文案跟着当前层走**。"在上面选一个 Scene 开始筛选"在刚进页面时是**错的**
  （那一层还没显示），会让用户去找一个不存在的东西。

**验证**：`_probe/review_funnel.py` 逐步断言层的可见性、计数与标签可读性：

| 步骤 | 断言 |
|---|---|
| 刚进来 | 地点/日期/关键词可见，**选场景隐藏** |
| 选一个地点（杭州市） | 选场景出现，`剩 84 / 303 个场景` |
| 撤掉地点 | 选场景收回，回到 `共 303 个场景` |
| 关键词筛一个**有区分度**的词 | 场景选项 85 → 2，条件叠加显示 |
| 阈值块 / 时段选择器 | 都不在 `.wb-steps` 内，且时段选择器仍在（可选项，不是被删掉） |
| 标签 | 不含 `\`、`_至_`、`_数字-` 这类目录名痕迹 |

> ⚠️ 关键词那条断言第一版失败，但那是**断言的问题不是功能的问题**：
> 用的词是 "2026"，而当时那批场景**全部**是 2026 年 —— 筛它当然筛不掉。
> 现在探针会自己从选项文本里挑一个"出现次数 < 总数"的词（如 `16:06`）。
>
> ⚠️ 另一条：我一度在 PowerShell 里看到 `captured_from=""` 就断言
> "日期筛选一直是坏的"，**那是误读**——列表开头那 26 个场景本来就没有日期
> （按 `captured_from` 排序，null 排最前）。单条复查证明 API 有值，
> 且日期比较在真实数据上正常（`2026-10-08` 命中 4/277 个场景）。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 顶栏筛选挤掉内容区高度 | 展开时**记住状态**；收起后只剩条件条一行；窄屏（<900px）改为浮层 |

## 八、验证手段（已有，本次继续用）

`C:\PhotoOS\_probe\`（不属产品代码）：

| 脚本 | 用途 |
|---|---|
| `run_all.py` | **一把跑完所有探针并出总表** —— 单支单支跑容易漏 |
| `ui_regress.py` | 七视图切换、截图、抓 JS 报错、断言条件条 |
| `deep_probe.py` | 点到二次点击才出现的组件，**真点一次**确认可用 |

| `library_filter.py` | 顶栏三维叠加、人物 AND、条件条复位 |
| `filter_layout.py` | **排版几何**：标题同基线、竖线统一、控件等高 |
| `maintenance_layout.py` | 维护页排版：逐行对齐、输入框与按钮同高（宽度可传参） |
| `modal_tags.py` | 弹窗三级渐进与标签交互 |
| `collections_grid.py` | 主题成员网格与弹窗所属主题 |
| `lint_backticks.py` | **静态守门**：HTML 注释里的反引号（会提前闭合模板串） |
| `bench_compose.py` | 组合层的真实数据基准与口径对拍 |
| `_edge.py` | 无头 Edge 助手（`taskkill /T` 杀整棵树） |

⚠️ 新增脚本一律用 `_edge.close()`，否则几十轮后残留进程会把测量污染
（实测把"弹窗 40 ms"变成 4049 ms）。

⚠️ 测量型断言一律**在对象可见时就地量**：隐藏元素的
`getBoundingClientRect()` 返回全零矩形，切走视图再量只会得到假的"没对齐"。

⚠️ 模板字符串内的 **HTML 注释不改变词法** —— 注释里的反引号照样提前闭合字符串
（曾让整个精选页只报一句 `field is not defined`）。`lint_backticks.py` 守这条。

⚠️ **无头 Edge 的 `--window-size` 不生效**（实测一律 500×320）。
量排版前先 `await _edge.set_viewport(call, w, h)`，并**回读打印真实视口** ——
否则"按不同宽度量"其实一直在同一个宽度上量，两次结果一样会被误读成"没响应"。
