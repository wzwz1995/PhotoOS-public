# 05 · AI 与向量

这一篇讲四件事：**两个图像编码器为什么并存**、**向量怎么存**、
**中文搜索为什么需要另一个 venv**、**Scene / Shot 分组怎么定的**。

---

## 一、两个编码器并存（都在 `library/`）

| | CLIP（`embedding.py`） | EmbeddingGemma 2（`embedding_gemma.py`） |
|---|---|---|
| 运行时 | onnxruntime | **torch** + sentence-transformers |
| 维度 | **512** | **768** |
| 干什么 | 视觉相似度 → Scene 划分 | **中文文字搜索** |
| 中文能力 | **几乎失效** | 中英跨语言对齐 33–67% |
| 速度 | 基准 | 慢约 7.4 倍 |

**为什么不能只留一个**：实测 `日出` 这个词，CLIP 的 dawn 富集是 **0.00**，
中文/英文富集比中位 **0.27**（CLIP 的跨语言对齐只有 2–18%）。
所以 CLIP 继续做它擅长的视觉相似度，EG2 专门服务中文查询。
`photoos search --engine` 只接受 `gemma` —— 不是漏实现，是 CLIP 中文实测不可用。

> ⚠️ **两个模型的向量并存**（`embedding` 表 21,400 × 2 = 42,800 行），
> 靠 `model` 列区分，**绝不能混用**。768 ≠ 512 是"并存的危险源"，
> 仓储层已按身份过滤。

### CLIP 那条路径的两个硬约束

1. **只下载 vision tower**（不需要文本塔，省 242 MB）。
2. **不让 CUDA 静默降级。** 三个条件必须同时成立：onnxruntime-gpu 的 CUDA 12 构建、
   `nvidia-cudnn-cu12` 指定版本、代码里显式调 `ort.preload_dlls()`。
   三种失败状态下 `get_available_providers()` 输出**完全相同**，
   `session.get_providers()` 在其中一种下**也骗人**
   —— 所以**唯一可靠的判据是跑一次真推理并计时**（`probe()` 干的就是这件事）。

模型缺失时返回 `NullEmbedder`，**绝不静默产出垃圾**：如果返回零向量，
相似度会全部变成 0，用户看到的是"所有照片都不像"。

### 编码的是 preview，不是原片

实测同图 preview→224 与原片→224 的余弦是 0.832–0.996，
而"不同图"只有 0.463–0.652 —— **两个分布不重叠**。
于是 IO 从 413 GB 降到 3.8 GB。

> ⚠️ **改过一次的错误前提（2026-10）。** 这一节原先接着写
> "而且 preview **已经烘焙了 EXIF 方向**" —— **这句是假的**。
> 3,861 张（其中 1,345 张 RAW）的 preview 方向是错的，因为
> `media/adapter.py` 把 LibRaw 的 `sizes.flip`（它只管**传感器原始数据**）
> 又用在了**相机内嵌的 JPEG 预览**上，造成二次旋转。
>
> 而这个错误前提正是它一直没被发现的原因：既然"已经烘焙好了"，
> 就没人再去核对。**详细定位、影响实测与修复步骤见
> [`13-raw-orientation.md`](13-raw-orientation.md)。**
>
> 实测影响**按模型完全不同**：CLIP 对 90°/180°/270° 都不敏感（余弦 ≥ 0.80），
> 所以内容检索基本没事；**SFace 对倒转是致命的（中位 0.105，36/36 张 < 0.3）**，
> 因为 `alignCrop` 会把倒着的脸对齐到倒的模板。

## 二、向量怎么存

表 `embedding`，`vector BLOB`，**float32 little-endian，长度 = dim × 4**。
显式指定字节序 —— 换机或换平台时字节序不能成为隐患。

**粒度是 asset，不是 shot**（尽管界面按 shot 去重）：

- 按 shot 存会造成循环依赖；
- 用户的目标是 text→image 检索，落在 asset 上更自然；
- 成本差可忽略（21,400 vs 7,997 向量 = 43.7 MB vs 16.4 MB）。

**身份 = `(asset_id, model, model_version, prep_version)`，UNIQUE。**
任何一项身份变化都**新增一行**，绝不 UPDATE 覆盖历史。

### 为什么不用 faiss / 向量数据库

实测 16,146 × 512 的单次 top-k 是 **0.24–0.27 ms**，全量两两 **0.88 s**
—— *"这比一次 SQLite 分页查询还便宜。"* 所以只用一个 `VectorStore` Protocol +
numpy 实现，不引入近似索引。

> 有个值得记住的性能教训：`decode_many` 早期是逐行解码 BLOB，
> 7,371 × 768 要 **42 秒**，而点积只要 **0.7 毫秒**。
> 批量 `np.frombuffer` 之后降到毫秒级。

### 流水线的性能分布

**推理只占端到端 6%，94% 是图像预处理。**

| 配置 | 吞吐 |
|---|---|
| 单线程预处理 + GPU | 19.8 img/s（≈18 分钟） |
| 8 线程预处理 + GPU | **111.3 img/s（≈3.2 分钟）** |

第一版漏了线程池，真实库演练实测 **1222 秒（20.4 分钟）**
—— *"计划的 3.2 分钟变成了 20 分钟（差 6 倍）"*。

## 三、⭐ 环境隔离：为什么中文搜索需要**另一个 venv**

这是本机最容易困惑的一点，务必理解。

`pyproject.toml` 把 AI 能力放在**可选依赖**里（`[ai-cpu]` / `[ai-gpu]` extra）。
产品 venv（`C:\PhotoOS\.venv`）**按设计不装** torch / onnxruntime / cv2。
而 EmbeddingGemma **没有 ONNX 产物**（官方仓库就没有），必须走 torch，
无法退化成 onnxruntime 路径。

于是本机的实际情况是：

| | 产品 venv `C:\PhotoOS\.venv` | AI venv `C:\PhotoOS\venv` |
|---|---|---|
| torch / sentence-transformers | ✗ | ✓ |
| onnxruntime / cv2 | ✗ | ✓ |
| `import photoos` | ✓（可编辑安装） | ✓（可编辑安装） |

**服务跑在产品 venv 里**，所以它自己**算不了**文字向量 ——
这就是界面上那句"这个页面所在的环境没有装它"的来源。

### 解决办法：`ai_python`

在 `data/config.json` 里指定执行界面命令所用的解释器：

```json
{
  "ai_python": "C:\\PhotoOS\\venv\\venv-eg2\\Scripts\\python.exe"
}
```

或环境变量 `PHOTOOS_AI_PYTHON`。留空 = 用服务自身的解释器。

> **本机已经配好了**（2026-10）。改动前请留意：这个路径指向本机的 spike venv，
> **换机器时要跟着改**。原始配置备份在 `data/config.json.bak-before-ai-python`。

配好之后（实测）：

| | 未配置 | 配置为 `venv` |
|---|---|---|
| 缺失依赖 | `torch, sentence_transformers, onnxruntime, cv2` | `[]` |
| 准备搜索词 | 不可用（失败信息说明原因） | **可用** |
| 人脸检测/特征 | 不可用 | **可用** |

界面上**执行环境**一栏会明确写出"用的是哪个 python、为什么" ——
因为*"命令到底在哪个环境里跑的"是排查一切 AI 问题的第一个问题*。

> 前提：那个解释器要能 `import photoos`（可编辑安装或已装包）。
> 验证方法：`<那个 python> -m photoos --version`。

#### 配好之后是什么样（真实一次执行）

在界面上点「立即准备」跑 `search 鸟 --save`：

## 四、Scene / Shot / Session 分组

三层，从细到粗：

```
asset（一张照片）
  └─ shot  拍摄组：连拍 / 同一机位的重复构图
       └─ scene  场景：一次拍摄
            └─ session  时段（半天 / 一次出行）
```

**`shot` 是这套系统的枢纽**：精选按组、主题按组、打包按组、语义命中也按组去重。
用户在界面上看到的"一格"几乎总是 shot，不是 asset。

### Shot 只用时间切

`shot_grouping.py` 只用时间 + `subsec`。测量结果把三个"看起来该用"的信号降级了：

| 信号 | 实测效果 | 结论 |
|---|---|---|
| 镜头 / 焦距 | **0/15、0/21** | 零效果 → 降为"置信度线索" |
| 文件名序列 | **0/15、0/21** | 零效果 → 同上 |
| 曝光变化 | **4/15、1/21** | 连拍中会变 → **绝不能当硬约束** |

`subsec` 是必需的：本机是 Nikon Z 5，`subsec` 100% 有值；
实测某个时段有 **46 对同秒相邻** —— 只靠秒级时间排序会乱。

一个 Shot 常见是 `jpeg+raw` 两文件（7,997 个 Shot 里 5,351 个是这种组合）。

### Scene 三步切分

1. 时间间隔 > 900 s 直接分；
2. 相似度合并 / 拆分（**没有嵌入时这一步退化，①③ 照常工作**）；
3. 尺寸上限 60 —— 这一步*"是'保证 PRD 标准可达'的机制，不是可有可无的优化"*。

**两个分组模块都刻意不含默认值** —— 避免"模块里藏一个默认值、配置里又一个默认值"
的双头局面。

## 五、人脸（Phase 4）

- **检测**：YuNet（`yunet-2023mar`）→ 表 `face`。这是**检测器的事实**。
- **特征**：SFace（`sface-2021dec`，128 维）→ 表 `face_embedding`。
- **聚类**：`photoos people discover` 把没人认领的脸聚成候选。

### 数据模型层面的纪律

- `person.name` **可以为空** —— 这不是偷懒：*"模型只能提出'这里有一簇脸'，
  **不知道那是谁**"*。命名是用户的事。
- `person_face.source` 区分"**你说的**"与"**模型提议的**"；
  只有你说的才算学习依据。
- `person_reject` 是独立表，让"不属于"成为**一等事实**（而不是靠"没在里面"暗示）。
- `face_verdict` 也是独立表：*"`face` 是检测器的事实……加一列 `is_person`
  会把人的判断混进事实表"*。
- `person_profile` 存每个人的正/负原型向量 + 判定线 `threshold` + `margin`
  —— 这就是"模型学到了什么"的实体。

### 界面上不做什么

**不给脸打分。** 模型确实算了一个相似度，但那是*"机器内部的判据，不是对人的评价"*。
所以：三档状态用**边框与徽标**区分，不用红黄绿、不用进度条、不用百分比；
相似度只在角落以极小灰字出现。

## 六、语义检索（Phase 3）

### 写入端（离线，需要 torch）

`photoos search "日出" --save` 算一次文本向量，并把**命中快照**写进
`semantic_query` / `semantic_query_hit`。

**为什么存快照**：界面拿 `semantic_query` 里那一行去和 `embedding` 做点积即可，
**不需要重跑文本塔** —— 这正是"产品 venv 没有 torch 也能显示搜索结果"的原因。

命中存的是 **shot_id 而不是 asset_id**：*"一个 Shot 就是一个决策单元，
界面本来就按 Shot 去重（实测 top-20 里只有 12 个独立 Shot，RAW+JPG 成对占名额）"*。

### 读取端（在线，numpy-only）

用户对结果表态（`semantic_feedback` 的 keep/drop）→ 服务端学出正/负向量
（`semantic_tuning`）→ 读取时重排：

```
score' = cos(x, text) + α·cos(x, pos_mean) − β·cos(x, neg_mean)
α = 0.35, β = 0.25, 最少 2 条反馈
```

三条纪律：

1. **原始结果永不覆盖** —— `semantic_query_hit` 保持模型当时的判断，
   重排只发生在读取端；
2. **每一步都可复算**；
3. **只用 numpy** —— 所以 `serve` 仍然不需要 torch / onnxruntime。

α 的上界有测试钉住：*"免得日后有人为了'效果更好'把它悄悄调大，
反而破坏了结果的稳定性"*。

## 七、模型存放

全部在 `<data_root>/ai_cache/models/` 下：

| 模型 | 文件 | 大小 |
|---|---|---|
| CLIP | `clip-vit-base-patch32-xenova-onnx-fp32/vision_model.onnx` | 351,685,709 B |
| EmbeddingGemma 2 | `embeddinggemma-2-safetensors-fp32/model.safetensors` | 1,488,915,288 B |
| 人脸 | YuNet + SFace | 约 37 MB |

放在 `data_root` 下的好处：**随数据根整体备份/迁移**（`ai_cache` 已在迁移包的
`DEFAULT_INCLUDE_DIRS` 里），且不依赖 venv 的生死。

下载**逐个校验 sha256**，落到 `<target>.photoos-part` 再原子改名；
校验失败就删掉。两个实测坑：镜像站对不带 UA 的小文件请求返回 403；
**不能用 ETag 当校验和**。

模型权重**不在 Python 包里** —— 用 `photoos ai fetch-model --engine …` 下载，
或在界面上点「下载 … 模型」。

## 八、命令一览

```powershell
# 环境自检（真跑一次推理计时）
photoos ai doctor

# 下载模型
photoos ai fetch-model --engine clip     # 约 335 MB（只下视觉塔；不含文字塔）
photoos ai fetch-model --engine gemma    # 约 1.45 GB
photoos ai fetch-model --engine face     # 约 37 MB

# 算向量（默认只预演，--apply 才写库）
photoos embed --engine clip  --apply
photoos embed --engine gemma --apply     # 需要 torch

# 中文搜索：算一个词的向量并落库
photoos search "日出" --save

# 人脸
photoos people detect --all
photoos people embed --all
photoos people discover
```

这些命令**都可以在界面上点按钮执行**（维护页 →「命令（界面直跑）」），
前提是 `ai_python` 配对了。见 [`07-runbook.md`](07-runbook.md) 排障一节。
