`C:\PhotoOS\_probe\` 下有一组脚本（**不属产品代码**，是开发期的检查工具）：

## 一、先看清楚：这四个页面**已经**是同一个东西

一个结论先说：**照片库 / 精选 / 找照片 / 人物不是四个页面，是同一台机器的四个入料口。**

依据（都能在代码里核对）：

| 已经共用的东西 | 证据 |
|---|---|
| **照片详情弹窗** | `openAssetDetail()` 只有一份定义（`app.js:629`），三个入口调它：照片库虚拟网格 `app.js:287`、找照片 `search.js:738`、人物页 `people.js:1354`（后两者用函数内动态 `import('./app.js')`） |
| **空态组件** | `.wb-empty` —— 16 处调用，遍布 `search / review / people / collections / pick_modal / app` |
| **加载态组件** | `loadingHtml()`（`shared.js:62`），统一成 `wb-empty.is-loading` |
| **状态徽标** | `.sel-badge`（样式在 `phase2.css:307`）+ `selectionClass()`（`shared.js:134`） |
| **缩略图入口** | `/api/assets/{id}/thumb`（及 `/preview`）这个 URL 模板在 **10 段**卡片里被**手写**了 10 遍（见下表） |

**所以缺口不是"要不要合并"，而是**：这套共性**没有被抽出来**，每个视图又抄了一遍。

### 重复的真身：**10 段**手写 asset 卡片标记（另有 2 段人脸卡）

先排除干扰：`/api/assets/${…}/thumb` 在整个前端出现 **11 次**，其中 1 次不归卡片管 ——
`app.js:687` 是**详情弹窗里视频的海报帧**。剩下 10 次是手写的卡片标记
（另外还有 2 处 `/view` 与 3 处 `/preview`，见下表的"用的图"列）：

| 位置 | 类名 | 用途 | 用的图 |
|---|---|---|---|
| `app.js:273` | `.card`（虚拟网格，DOM 复用池） | 照片库 | `/thumb` |
| `search.js:698` `buildCard` / `:768` `updateCard` | `.search-card` | 找照片 | `/thumb`（`:704` / `:770`） |
| `review.js:750` | `.compare-card` | 精选 · 并排比较 | **`/preview`**（`:751`） |
| `review.js:845` | `.grp-thumb` | 精选 · 相似组缩略图 | `/thumb`（`:846`） |
| `review.js:1147` `renderAdjust` | `.adjust-row` | 精选 · 调整分组勾选表 | `/thumb`（`:1150`） |
| `collections.js:36` | `.collection-card` | 主题列表封面 | `/thumb` |
| `collections.js:59` | `.ci-thumb` | 主题详情成员 | `/thumb` |
| `pick_modal.js:99` | `.wb-pick` | 「加入主题」选择格 | `/thumb`（`:100`） |
| `pick_modal.js:323` | （同族） | 「加入主题」搜索结果的格 | `/thumb`（`:324`） |
| `people.js:160` `faceCard` | `.person-face` | 人物 · 人脸墙 | **`/api/faces/{id}/thumb?size=112`** |
| `people.js:80` | 人物列表封面 | 人物 · 左栏头像 | 同上 |

**关键区分**：上面前九行用的是 **asset 图**，抽成一个 `buildAssetCard` 是天经地义
（它要接的参数里因此有 `size: 'thumb' | 'preview'`，不是写死一种）；
人物页那两行用的是 **face 缩略图**（`/api/faces/…`），**不该被强行合并** ——
它们显示的是"一张脸"，不是"一张照片"，尺寸、比例、语义都不同。
人物页要共用的只是**外壳**（`.pf-when` / `fileButton` / `pf-pick` 的排布与样式），
不是图源。把这两件事混在一起抽，会得到一个谁都不合身的组件。

（人物页的 `fileButton`（`people.js:149`）已经是那套共性的**局部实现**：
文件名 + 「看原片」+ `data-asset`，注释还专门写了路径转义的坑 ——
这正说明这套逻辑值得提到一处，而不是每个模块各自踩一遍。）

### 顺带查出来的三个真缺口

这三条不是"样式不统一"，是**功能不一致**。抽外壳的同时应当一并补掉，
因为它们本来就是"同一件事被实现了三遍、其中一遍漏了"的结果：

1. **主题里打不开单张照片。** `collections.js:55` 的 `.collection-item` 有缩略图、
   有文件名、有时刻 —— 但文件名是**死的文本**，没有 `data-asset`，也没有
   `data-act="asset"` 的处理分支。整个 `collections.js` 里**没有** `openAssetDetail`
   的调用（`:114` 那次 `import('./app.js')` 调的是 `exportPack`，是导出图包）。
   用户在主题里看到一张照片，想看大图/看完整路径，**没有入口**。
2. **「加入主题」弹窗里的照片也打不开。** `pick_modal.js:99` / `:323` 两处同理，
   只有一个"选择"语义。
3. **`data-act="asset"` 这个协议只有一个消费者。** 它定义在 `people.js:156`、
   在 `people.js:1304` 被派发 —— 也就是说"文件名 = 看原片"这个约定
   实际上只服务于人物页。这正是一个**该统一而没有统一**的协议。

**补法**（属于第 2、3 步的一部分）：把 `fileButton` 的语义提升为卡片原语的一部分 ——
**凡是卡片上的文件名都是原片入口**。这样主题与「加入主题」自动获得该能力，
且不必各自再写一遍转义。


### 为什么这件事值得做

不是"代码整洁"，是**用户能感觉到的四个症状**：

1. **换个视角就不知道自己在哪。** 四个页面各有自己的一套筛选控件，没有任何地方
   告诉你"当前是什么条件"。在照片库筛到"杭州市 2024 年"，切到找照片要重新说一遍；
   切回来又要再说一遍。
2. **同一件事在不同页面上手感不同。** 卡片 hover、选中态、空态文案、加载态
   在十段实现里各有细节差异 —— 用户会以为是不同功能的两种东西。
3. **"回到全库"没有出口。** 筛着筛着想知道"整个库还有多少"，只能重新点一遍浏览轴。
4. **同一件事有的页面能做、有的不能。** 照片库/找照片/人物都能点开单张照片，
   主题和「加入主题」弹窗不能（见上节三个真缺口）。

## 三、要抽的三样东西

### 3.1 条件条（`.query-bar`）—— 解决"我是谁、我在筛什么"

**契约**：把"当前的查询意图"渲染成**一行可读的摘要 + 可逐个移除的芯片**。

```
[关键词: 日落 ×] [杭州市 ×] [2024 年 ×] [镜头: 24-70 ×] [焦距: ≤35 ×]   共 1,234 张 · 回到全库
```

三处已有的查询状态**形状其实相同**，都能映射到这个模型：

| 来源 | 现有状态 | 映射成芯片 |
|---|---|---|
| 照片库 | `state.filters`（`app.js`）+ `state.browse.chain` | 每个非空筛选一个芯片；每个浏览层级一个芯片 |
| 找照片（内容） | `state.current.query_text` | 一个"搜索词"芯片 |
| 找照片（时间地点） | `find-city` / `find-session` / `find-from` / `find-to` | 四个条件各一个芯片 |
| 精选 | `state.filter`（city / date / keyword）+ `state.sessionId` | 同上 |
| 人物 | 无查询条件（是人脸聚类） | **不显示条件条**，只显示"当前人物" |

**关键设计决定**：

- **芯片是"移除"而不是"编辑"** —— 点 × 就少一个条件，立即重查。
  编辑仍然回到各自页面原有的控件（那里有下拉框、日期选择器、滑块）。
  这样条件条只做"汇总 + 撤销"，不重复实现一遍输入控件。
- **右侧永远有「回到全库」** —— 这是症状 3 的解法，成本极低。
- **条件条不引入新状态。** 它是**只读投影**：从各页面已有的 state 算出来。
  这样它可以随时加上去、随时拿掉，不会成为第五套状态。
- **条件条里不得出现配置文件的字面名。** 只说人话（"跟随全局默认"），
  不提任何配置文件名 —— 界面上出现 `config.json` 这类字符串是不专业的，
  后端已经在 `api/app.py` 里做过这层转换，前端不要退回去。

**不做什么**：不做"跨页保持筛选"（那是另一个功能，需要 URL 或 sessionStorage
持久化，且会带来"为什么这里还筛着"的困惑）。条件条只解决"看得见 + 撤得掉"。

### 3.2 卡片原语（`buildAssetCard` / `updateAssetCard`）—— 解决"十段手写"

**契约**：一个函数产出卡片 DOM，**接缝（slot）留给各页面**。

```js
// 新的 cards.js（或 shared.js，看体量）
export function buildAssetCard(item, {
  size = 'thumb',          // thumb | preview
  badge = true,            // 是否显示精选状态徽标
  onOpen,                  // 「看原片」→ openAssetDetail(asset_id)
  extra = null,            // 各页面自己的附加区（返回 DOM 或 HTML 串）
} = {})

export function updateAssetCard(node, item, opts)  // 就地改，不重建
```

**统一的部分**（十段都有，且应当一模一样）：

- 图：`size` 决定 `/thumb` 还是 `/preview`（比较卡要看得清，其余用缩略图）；
- 文件名（`baseName`，等宽、超长省略号）；
- 拍摄时刻（`formatWhen`，等宽、tabular-nums）；
- 精选状态徽标（`sel-badge` + `selectionClass()`）；
- 「看原片」入口 → `openAssetDetail(asset_id)`；
- 焦点环与 hover（用 `--focus` / 描边亮起，全应用一套）。

**各页面自己填的部分**（`extra`）：

| 页面 | 附加什么 |
|---|---|
| 找照片 | 「我要这种 / 不是这种」两个表态按钮 + 多选勾 + 相似度小字 |
| 精选（比较） | 1/2/3 三档按钮 + 选中理由 |
| 精选（调整分组） | 复选框 + 自定义名字（`item.name`） |
| 主题 | 序号 + 移出按钮 |
| 「加入主题」 | 已加入态 |
| 照片库 | 无（最朴素的那一种） |

**人物页只共外壳、不共图源。** 人脸卡显示的是"一张脸"（`/api/faces/{id}/thumb`，
`size=112` 是正方形脸裁切），不是"一张照片"。强合并会得到一个方形比例与
16:9 缩略图互斥的组件。人物页共用的是排布与样式约定（`pf-when` / `fileButton`
/ `pf-pick`），并**复用 `fileButton` 那套"文件名即原片入口"的实现** ——
顺便消掉一处重复的转义注释。

**判据**：抽完之后，`/api/assets/${…}/thumb` 这个模板在视图模块里
**只应出现在 `cards.js` 一处**（详情弹窗内部的大图是另一回事，不在此列）。

**注意**：照片库那张卡不能直接用 `buildAssetCard` —— 它的虚拟网格**复用 DOM 节点**
（`contain: strict`，只渲染可见格）。这正是把原语**一开始就拆成 `build` + `update`
两个函数**的原因：找照片的 `updateCard`（`search.js:768`）已经是这个形状，
两者可以对上。如果只提供一个"返回 HTML 串"的函数，
那个 100k 张也不卡的虚拟网格会被毁掉。

### 3.3 结果壳（`.result-shell`）—— 解决"状态长得不一样"

四处的**加载 / 空 / 错误 / 有内容**四态，现在各写各的。统一成一个壳：

```
.result-shell
  ├─ 条件条（3.1）
  ├─ 状态区（加载 / 空 / 错误 —— 一律走 .wb-empty，已是既有组件）
  └─ 结果区（网格 / 列表 —— 各页面自己填）
```

**它不接管渲染**，只保证四态的形状一致：什么时候显示加载、什么时候显示空态、
错误怎么呈现（`wb-empty` + 失败原因 + 可照做的下一步）。

## 四、实施顺序（六步，每步独立可用）

**这一步很关键**：每一步结束都应当是可发布状态，不能出现"做到一半两边都不能用"。

| 步 | 内容 | 风险 | 验证 |
|---|---|---|---|
| **1** | 抽出 `buildAssetCard` / `updateAssetCard`，**只在找照片**接上 | 低 | 找照片逐项截图对比；`git diff` 里视图代码净减 |
| **2** | 接上主题两处（`collections.js:36` / `:59`）与「加入主题」两处（`pick_modal.js:99` / `:323`） | 低 | 两处截图对比；「看原片」仍落到同一个弹窗 |
| **3** | 接上精选三处（比较 / 相似组 / 调整分组），**人物页只共外壳与 `fileButton`** | 中 | 三处截图对比；精选的键盘流与调整分组勾选行为不变 |
| **4** | 加 `.query-bar`：**先只在照片库**（它的 state 最结构化） | 低 | 芯片增删与筛选结果一致；「回到全库」回得去 |
| **5** | 条件条接到找照片两种模式 + 精选 | 中 | 每个条件都能单独撤掉；撤掉后结果与直接改控件一致 |
| **6** | 结果壳统一四态；清理各页面残留的自绘状态 | 中 | 断网/空库/加载中三种情况逐一目视 |

**照片库的虚拟网格放在最后**（可选）：它的 DOM 复用池与卡片原语的 `update`
语义兼容，但要小心 `contain: strict` 与 `relayout()` 的调用时机。
如果风险收益不划算，**可以永远不接** —— 它只有一张卡，重复的成本最低。

## 五、为什么不做方案 B（合并成一个页面）

留个记录，免得以后有人重新提：

| | 方案 A（本文） | 方案 B（合并） |
|---|---|---|
| 入口 | 4 个，各有明确任务 | 1 个，顶部切模式 |
| 照片库的目录树 | 保留（左栏 + 网格） | **失去**横向两栏形态 |
| 精选的键盘流 | 保留 | 塞进一个 tab，容易变成"四页挤一页" |
| 用户要改的习惯 | 不变 | 要重新学一遍入口 |

方案 B 的收益是"只有一个入口"，代价是**每个页面最好用的那个形态**。
而现在用户真正的痛（不知道自己筛了什么、同一件事手感不同）**方案 A 就能解决**。

**若将来仍觉得入口太散**：先做完 A，那时共性已经抽干净，B 就只是把四个壳
摆到一个页面里 —— 顺水推舟，而不是重新设计。

## 六、不能碰的约束（写在这里，动手前必读）

1. **不引入"评分/推荐"表达**（PRD §9.2 LOCKED）。
   统一之后尤其危险：很容易在条件条上加一句"为你推荐"或在卡片上加个星级。
   **金色 = 你的选择/当前项，不是"更好"。**
2. **"当前项"只有两种画法**（[`06-frontend.md`](06-frontend.md) 第三节）：
   切页/页内模式 = 金色下边框；页内分段 = 皇家蓝实心。新组件必须选一个，不能自创。
3. **令牌只在 `tokens.css` 定义**。新组件的颜色/圆角/字号一律用现有令牌，
   不新增第 6 级圆角、不新造字号。
4. **`.wb-empty` 是唯一的空态组件**。内嵌在 `.panel` 里时它自动去框（已有规则）。
5. **零构建**。不引入打包器、不引入框架、不引入 npm 依赖。
   新模块仍然是原生 ES module，仍然遵守 `shared.js` 那条"不得有顶层副作用"的纪律。
6. **`app.js` 不能被静态 import**（它在模块顶层 `boot()`）。
   需要用它的能力时，一律**函数内**动态 `import('./app.js')`。
7. **原片只读**。卡片只引用 `/api/assets/{id}/thumb` 与 `/preview`，绝不碰原图路径。
